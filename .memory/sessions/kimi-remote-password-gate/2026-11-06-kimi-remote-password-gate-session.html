# kimi-remote password gate — session digest (2026-11-06)

## Trigger
- kimi-remote printed `https://host/#token=<bearer>` + QR: anyone who saw the QR had full shell access.
- User: QR must carry no credential; a memorable password (never in the QR) gates access; prefer auth embedded in the used tools if any.

## Evidence
- `kimi_remote.py`: single-file stdlib launcher; tailscale serve / cloudflare quick tunnel → kimi web; token from `~/.kimi-code/server.token`.
- `kimi web --help`: bearer-token auth on REST+WS; no password feature; `--dangerous-bypass-auth` exists but AGENTS.md bans it.
- cloudflared quick tunnels: no auth feature; Cloudflare Access needs own domain + named tunnel → cannot protect `*.trycloudflare.com`.
- tailscale serve: no auth layer; tailnet membership is the only implicit credential.
- kimi web UI auth = `Authorization: Bearer` set by JS; JS cannot set headers on WebSocket handshakes → HTTP Basic in a proxy would collide / be missing on WS.

## Model
phone → tunnel → gate (127.0.0.1:GATE) → kimi web (127.0.0.1:KIMI)
- `gate_conn`: read request head (≤64KB) → cookie `kr_auth` (per-run `secrets.token_urlsafe(32)`, `hmac.compare_digest`) valid → splice raw TCP both ways (WS-safe).
- `POST /__login`: password (body ≤8KB, parse_qs) → 302 `Location: /#token=<token>` + `Set-Cookie: kr_auth=…; HttpOnly; Secure; SameSite=Strict`; wrong → 401 form.
- Anything else unauthenticated → 401 + password form. Bearer-only access through the tunnel is now impossible (password first, then token).
- Password source: `KIMI_REMOTE_PASSWORD` env, else getpass prompt with confirm; non-TTY without env → die.
- Ports: gate = free_port(--port), kimi = free_port(gate+1); tunnels target the gate port.
- Per-run cookie secret → restart = phone re-login (intended).

## Hypothesis → verification
- `--self-test` (dummy loopback upstream): 401 no/bad cookie, API POST blocked, wrong pw 401, right pw 302 `/#token=TOK` + cookie, relay 200. PASS.
- Live vs real kimi web 2.4.0 on loopback: same checks PASS; `/api/v1/meta` 401 without bearer, 200 with bearer → kimi's own auth intact behind the gate.
- Tunnel e2e NOT run: cloudflared not installed (stale PATH entry), tailscale BackendState=NoState. Documented, not silently skipped.

## Decisions
- Cookie, not HTTP Basic (Bearer header collision; WS cannot set Authorization).
- Token bootstrap via 302 fragment; dropped the "paste this token" fallback print (QR no longer carries a fragment, nothing to strip).
- Gate always on in both modes; no `--password` CLI arg (shell history leaks).
- `wait_port` → `wait_ready`: TCP accept ≠ HTTP ready; poll `GET /api/v1/meta` until any HTTP response (401 = warm); timeout 20s → 90s; one-time "warming up" notice after 3s. The probe itself is the warm-up.
- Rejected: browser-window warm-up (gated URL is 401'd by the gate itself → never reaches kimi; pops a window; token lands in browser history).
- Rejected: Cloudflare Access (needs domain + Zero Trust + named tunnel; useless for tailscale mode).

## Incident: "first gated run didn't work until manual kimi web"
- Root cause: cold first boot (bundled exe self-extract + first-run init) exceeded the 20s TCP-only wait; the user's manual `kimi web` run absorbed the one-time cost, so later runs were warm. Fixed by `wait_ready` (90s, HTTP-level, warming notice).

## Open risks
- No rate-limit on `/__login` (loopback tool; token still behind the gate). Add if URL exposure becomes likely.
- Full tunnel e2e with the gate unverified on this machine (needs `tailscale up` or cloudflared install); run the README/AGENTS.md curl checks once available.
- Two consecutive Edit calls on kimi_remote.py once ate a `def free_port` header — caught by re-read; lesson: re-read after chained edits.
